# Prerequisites and the deploy recipe

The skill is portable Python and Markdown. What it *depends on* is not in this
folder, so read this before handing it to someone else.

## What the machine must already have

| Requirement | Why | Check |
|---|---|---|
| Exasol Personal Local Starter Kit | supplies the database and `exapump` | `exakit status` |
| `exapump` on `PATH`, profile `starter-kit` | **`profile_schema.py` and `signal_check.py` shell out to `exapump sql -f json`.** Without it, stage 3 cannot run at all | `exapump sql -p starter-kit 'SELECT 1'` |
| Data loaded in a schema | the card is built from a live database, never from a file | `exakit status` lists datasets |
| `dash-server` add-on, running | hosts the dashboard and exposes the MCP control plane | `exakit status` shows `dash-server: running` |
| The `dash-server` skill | stage 6 drives the control plane through it | listed in the agent's skills |
| `ANTHROPIC_API_KEY` (optional) | semantic text-to-SQL; without it the panel falls back to template matching | see CHANGES.md item 14 |

The SQL this skill emits is **Exasol dialect** (`TO_DATE`, `ADD_MONTHS`,
`DAYS_BETWEEN`). It is portable across datasets, not across databases.

## The deploy recipe — scaffold first, then overwrite

`build_dashboard.py` does **not** emit `dash_server_exasol.py`, the runtime
helper every hosted app imports. Creating an app straight from the built files
therefore fails validation:

    Import smoke check failed: FileNotFoundError:
    .../dash_server_exasol.py

That helper is auto-generated by dash-server itself, so it is not vendored here
— a copy would drift with the add-on's version. Let dash-server write it:

1. **Scaffold**, which supplies the helper and binds the Exasol profile:

       app_create_exasol_dashboard{name: "<app>", profile_name: "starter-kit"}

2. **Overwrite** with the built workspace — every file *except*
   `dash_server_exasol.py` (leave dash-server's) and `dash-app.json` (the
   scaffold already bound the profile):

       app_put_files{name: "<app>", files: [...]}

3. **Deploy** and check the probes:

       app_deploy_draft{name: "<app>", deployment_target: "live",
                        auto_rollback_on_health_failure: true}
       app_run_healthcheck{name: "<app>"}

   `force_clean: true` on the deploy when `requirements.txt` changed, so the
   dependency install is not served from cache.

Verified with `titanic-safety` on 2026-08-26: scaffold, then eleven files, then
deploy — healthy on every probe with nothing copied by hand.

`app_create_from_files` also works, but only if you supply the helper yourself.
Prefer the recipe above.

## Where the skill has to live

The agent loads skills from `.claude/skills/` (or `~/.agents/skills/`). In this
repository `.claude/` is **gitignored**, so cloning does not deliver the skill —
ship this folder separately, or un-ignore the path.
